KBA: Verificar e solucionar problemas de serviços pela linha de comando

Sintoma. Um recurso do firewall (DNS, VPN, IPS, proteção web, o link com o controller) não se comporta bem e a interface web não diz por quê.

Aplica-se a. Nexwall Firewall 26.2.1. Os comandos rodam como root por SSH, pelo console ou pelo terminal do controller. Qual serviço sustenta cada recurso está na Referência de comandos de serviços e logs.

1. Pergunte ao serviço o status dele​

/etc/init.d/dnsmasq status
running

Confira vários de uma vez:

for s in firewall dnsmasq nginx dropbear ns-plug snort mwan3 ns-ui dpi openvpn; do
  printf "%-12s %s\n" $s "$(/etc/init.d/$s status 2>&1 | head -1)"
done
firewall     active with no instances
dnsmasq      running
nginx        running
dropbear     running
ns-plug      running
snort        running
mwan3        running
ns-ui        not running
dpi          not running
openvpn      active with no instances

2. Como ler a resposta​

not running nem sempre é uma falha. A palavra depende de como o serviço é construído:

RespostaSignificadoFalha?
runningUm processo de longa duração está ativoNão
active with no instancesO serviço está habilitado mas não tem nada para executar, por exemplo openvpn sem túnel configurado, ou firewall, que apenas carrega regrasNão, a menos que você tenha configurado algo que dependa dele
not runningNenhum processo está ativo agoraDepende: um serviço que deveria ficar no ar está parado (falha), ou é um serviço de execução única que cumpriu a tarefa e saiu (normal)

ns-ui, dpi e ns-binding são serviços de execução única nesta versão. Comprove pedindo os detalhes ao gerenciador de serviços:

ubus call service list '{"name":"dpi"}'
{ "dpi": { "instances": { "instance1": { "running": false, "command": [ "/usr/sbin/dpi" ], "exit_code": 0 } } } }

Captura: status de dez serviços; ns-ui e dpi dizem "not running" mas terminaram normalmente (exit_code 0).

"running": false com "exit_code": 0 significa que o programa terminou normalmente. Uma falha real mostra um exit_code diferente de zero, ou uma instância que reinicia sem parar. Confirme sempre pelo efeito: uma interface web que abre, ou um bloqueio de DPI no log, dizem mais que a palavra "running".

Para um serviço em execução, a mesma chamada devolve o pid e a linha de comando exata, que mostra qual arquivo de configuração ele lê:

/etc/init.d/dnsmasq info

3. Está habilitado na inicialização?​

/etc/init.d/dnsmasq enabled && echo yes || echo no

Um serviço que funciona ao iniciá-lo manualmente e some depois de um reinício não está habilitado. Use /etc/init.d/<serviço> enable.

4. Está escutando e responde?​

netstat -tulnp | grep -E 'dnsmasq|dropbear|nginx'
tcp   0.0.0.0:22         LISTEN   5645/dropbear
tcp   192.168.1.1:53     LISTEN   103916/dnsmasq

Depois teste o serviço pela rede, como um cliente faria: nc -zv -w3 <ip> <porta> ou dig @<ip> <nome>. Veja a KBA de conectividade.

5. Leia o log​

Todos os serviços registram em /var/log/messages, cada um com o próprio nome (a coluna Find it in the log da referência de serviços).

grep -i ns-plug /var/log/messages | tail -5
tail -f /var/log/messages | grep -i dnsmasq

A mesma busca está disponível como uma única chamada ubus, que é a que a página Logs da interface web usa:

ubus call ns.log get-log '{"search":"dropbear","limit":2}'
{ "values": [
    "Nov 19 19:45:08 FIREWALL.lan dropbear[102974]: Child connection from 192.168.0.8:52414",
    "Nov 19 19:45:08 FIREWALL.lan dropbear[102974]: Password auth succeeded for 'root' from 192.168.0.8:52414" ] }

Leia as linhas em volta do momento da falha. Mensagens como EMSGSIZE Path-MTU=1420, refused, timed out, failed e cannot são as primeiras a observar. Esta unidade não tem logread; veja Logs e depuração.

6. Confira a configuração antes de reiniciar​

Reiniciar com a configuração quebrada transforma um problema pequeno em uma parada. Valide antes, onde o serviço permitir:

ServiçoVerificação
dnsmasqdnsmasq --test imprime syntax check OK.
IPS (snort)snort-mgr check valida a configuração gerada sem aplicá-la
Qualquer ajuste UCIuci show <config> mostra o que o serviço vai ler; veja Entendendo o UCI

7. Reiniciar ou recarregar​

/etc/init.d/firewall reload     # aplica regras sem derrubar conexões
/etc/init.d/dnsmasq restart     # breve interrupção

Tente reload primeiro onde existir. O restart interrompe o serviço por um instante, então numa unidade em produção faça quando for aceitável. Não reinicie o keepalived diretamente em um par de alta disponibilidade; use o ns-ha-config. Depois repita os passos 1 e 4 e leia o log de novo.

8. Status específico de cada recurso​

Quando as verificações genéricas passam e o recurso continua com problema, o recurso tem o próprio comando de status:

RecursoComando
Link com o controllerubus call ns.plug status
SD-WANmwan3 status
WireGuardwg show
IPsecswanctl --list-sas
IPSsnort-mgr status
Alta disponibilidadens-ha-config status

9. Pouca memória é uma causa oculta frequente​

O sistema para serviços quando a memória acaba, e os recursos de filtragem (IPS, filtragem de DNS, proteção web) são os que mais consomem.

free
snort-mgr status
              total        used        free      shared  buff/cache   available
Mem:        2009240     1254832      184416       68744      569992      612240
Total system memory=1962.148M  Used=1786.797M (91.1%)  Free=175.352M (8.9%)

Os valores estão em kilobytes. Se available estiver muito baixo, ou serviços reiniciarem sem motivo aparente, procure linhas de memória esgotada com grep -i "out of memory\|oom" /var/log/messages | tail e considere desligar as listas ou recursos de que não precisa. A página de filtragem de DNS mostra quanta memória as listas ativas exigem.
