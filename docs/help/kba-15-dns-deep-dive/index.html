KBA-15: Troubleshoot DNS from the command line

Symptom. A site or service "does not open", but pinging its IP address works. Or a name resolves from your laptop and not from the LAN.

Applies to. Nexwall Firewall 26.2.1. Commands run as root over SSH, the console or the controller terminal.

:::note What is installed dig and nslookup are installed and work out of the box. host is not installed, and neither is telnet (see the connectivity KBA for the replacements). If a command says not found, check the spelling and use command -v <name> before assuming a fault. :::

1. Ask the unit's own resolver​

dig nexwall.com.br
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 60522
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
nexwall.com.br.		3594	IN	A	191.252.111.19

;; Query time: 0 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)

Screenshot: dig answered by the unit's own resolver, status NOERROR.

Read three things: status, the ANSWER SECTION and the SERVER line. The server is 127.0.0.1, the resolver of the firewall itself (dnsmasq). For a short answer, add +short:

dig +short nexwall.com.br
statusMeaningNext step
NOERROR with an answerThe name resolvesThe problem is not DNS, go to the connectivity KBA
NOERROR with no answerThe name exists but has no record of that type (for example, no AAAA)Try dig A <name> and dig AAAA <name>
NXDOMAINThe name does not existCheck the spelling, then compare with a public resolver (step 2)
SERVFAILThe upstream server could not answerTest the upstream servers (step 3)
communications error ... timed outThe server did not answer at allThe resolver is down or unreachable (step 4)

2. Compare with a public resolver​

Ask a public server directly, bypassing the firewall's resolver:

dig +short nexwall.com.br @8.8.8.8
191.252.111.19

Screenshot: NXDOMAIN for a name that does not exist, and a public resolver answer for comparison.

Firewall resolverPublic resolverConclusion
FailsWorksThe problem is inside the firewall: dnsmasq, its upstream servers, or DNS filtering
WorksWorksDNS is fine; look at the client (its DNS setting, a cache, a VPN or a proxy on the PC)
FailsFailsThe name really does not resolve, or the firewall has no internet. Check the WAN first

DNS filtering can also change what a name resolves to, so a filtered category looks like a DNS problem on the client. When one site fails and the rest work, compare the two answers and check the filtering lists before looking elsewhere.

3. Check the upstream servers​

The firewall forwards to the servers it received from the provider or that you set on the DNS & DHCP page.

cat /etc/resolv.conf
cat /tmp/resolv.conf.d/resolv.conf.auto
search lan
nameserver 127.0.0.1
nameserver ::1

/etc/resolv.conf always points at the firewall itself. The servers it forwards to are in resolv.conf.auto, one block per interface (here the WAN, whose gateway also acts as the resolver):

# Interface wan
nameserver 192.168.0.1
search Home

Test each upstream server:

dig +short nexwall.com.br @<upstream-server> +time=3 +tries=1

A server that times out is the one to remove or replace. Two or more working servers avoid a single point of failure.

4. A timeout: is the resolver reachable?​

dig +short nexwall.com.br @10.255.255.1 +time=2 +tries=1
;; communications error to 10.255.255.1#53: timed out
;; no servers could be reached

That is what an unreachable server looks like (the exit code is 9). Next:

/etc/init.d/dnsmasq status
netstat -tulnp | grep ':53 '
running
tcp   0   0 192.168.1.1:53   0.0.0.0:*   LISTEN   103916/dnsmasq
udp   0   0 192.168.1.1:53   0.0.0.0:*            103916/dnsmasq

If dnsmasq is not running, or nothing listens on the LAN address, restart it and read its log:

/etc/init.d/dnsmasq restart
grep dnsmasq /var/log/messages | tail -20

To check the configuration without restarting:

dnsmasq --test
dnsmasq: syntax check OK.

5. Follow the resolution from the root​

When the answer is wrong, or only some names fail, trace the whole path:

dig +trace nexwall.com.br

The trace goes from the root servers down to the authoritative ones. Lines such as UDP setup ... failed: network unreachable for IPv6 addresses are normal on a network without IPv6; look at the last line, which gives the final answer and where it came from.

6. Quick reference​

TaskCommand
Resolve with the unit's resolverdig <name>
Short answer onlydig +short <name>
A specific record typedig MX <name>, dig AAAA <name>, dig TXT <name>
Use a specific serverdig @1.1.1.1 <name>
Reverse lookupdig -x <ip>
Full path from the rootdig +trace <name>
Same with nslookupnslookup <name> or nslookup <name> <server>
DNS over HTTPSdig +https @8.8.8.8 <name>
Capture DNS traffic on the WANtcpdump -i <wan-interface> -n udp port 53
