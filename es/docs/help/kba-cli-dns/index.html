KBA: Solucionar problemas de DNS desde la línea de comandos

Síntoma. Un sitio o servicio "no abre", pero hacer ping a su dirección IP funciona. O un nombre se resuelve desde su portátil y no desde la LAN.

Se aplica a. Nexwall Firewall 26.2.1. Los comandos se ejecutan como root por SSH, por la consola o desde el terminal del controller.

:::note Qué está instalado dig y nslookup están instalados y funcionan de fábrica. host no está instalado, ni tampoco telnet (vea en la KBA de conectividad los sustitutos). Si un comando responde not found, revise la ortografía y use command -v <nombre> antes de suponer una falla. :::

1. Pregunte al resolutor de la propia unidad​

dig nexwall.com.br
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 60522
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
nexwall.com.br.		3594	IN	A	191.252.111.19

;; Query time: 0 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)

Captura: dig respondido por el resolvedor de la propia unidad, estado NOERROR.

Lea tres cosas: status, la ANSWER SECTION y la línea SERVER. El servidor es 127.0.0.1, el resolutor del propio firewall (dnsmasq). Para una respuesta corta, añada +short:

dig +short nexwall.com.br
statusSignificadoSiguiente paso
NOERROR con respuestaEl nombre se resuelveEl problema no es DNS, pase a la KBA de conectividad
NOERROR sin respuestaEl nombre existe pero no tiene registro de ese tipo (por ejemplo, sin AAAA)Pruebe dig A <nombre> y dig AAAA <nombre>
NXDOMAINEl nombre no existeRevise la ortografía y compare con un resolutor público (paso 2)
SERVFAILEl servidor de salida no pudo responderPruebe los servidores de salida (paso 3)
communications error ... timed outEl servidor no respondió en absolutoEl resolutor está caído o inalcanzable (paso 4)

2. Compare con un resolutor público​

Pregunte directamente a un servidor público, sin pasar por el resolutor del firewall:

dig +short nexwall.com.br @8.8.8.8
191.252.111.19

Captura: NXDOMAIN para un nombre que no existe y la respuesta de un resolvedor público como comparación.

Resolutor del firewallResolutor públicoConclusión
FallaFuncionaEl problema está dentro del firewall: dnsmasq, sus servidores de salida o el filtrado de DNS
FuncionaFuncionaDNS está bien; mire el cliente (su configuración DNS, una caché, una VPN o un proxy en el PC)
FallaFallaEl nombre realmente no se resuelve, o el firewall no tiene internet. Revise primero la WAN

El filtrado de DNS también puede cambiar a qué se resuelve un nombre, así que una categoría filtrada parece un problema de DNS en el cliente. Cuando un sitio falla y el resto funciona, compare las dos respuestas y revise las listas de filtrado antes de buscar en otro lado.

3. Revise los servidores de salida​

El firewall reenvía a los servidores que recibió del proveedor o que usted definió en la página DNS y DHCP.

cat /etc/resolv.conf
cat /tmp/resolv.conf.d/resolv.conf.auto
search lan
nameserver 127.0.0.1
nameserver ::1

/etc/resolv.conf siempre apunta al propio firewall. Los servidores a los que reenvía están en resolv.conf.auto, un bloque por interfaz (aquí la WAN, cuya puerta de enlace también actúa como resolutor):

# Interface wan
nameserver 192.168.0.1
search Home

Pruebe cada servidor de salida:

dig +short nexwall.com.br @<servidor-de-salida> +time=3 +tries=1

Un servidor que no responde es el que hay que quitar o reemplazar. Dos o más servidores que funcionen evitan un único punto de falla.

4. Un tiempo de espera agotado: ¿se alcanza el resolutor?​

dig +short nexwall.com.br @10.255.255.1 +time=2 +tries=1
;; communications error to 10.255.255.1#53: timed out
;; no servers could be reached

Así se ve un servidor inalcanzable (el código de salida es 9). A continuación:

/etc/init.d/dnsmasq status
netstat -tulnp | grep ':53 '
running
tcp   0   0 192.168.1.1:53   0.0.0.0:*   LISTEN   103916/dnsmasq
udp   0   0 192.168.1.1:53   0.0.0.0:*            103916/dnsmasq

Si dnsmasq no está en ejecución, o nada escucha en la dirección de la LAN, reinícielo y lea su registro:

/etc/init.d/dnsmasq restart
grep dnsmasq /var/log/messages | tail -20

Para comprobar la configuración sin reiniciar:

dnsmasq --test
dnsmasq: syntax check OK.

5. Siga la resolución desde la raíz​

Cuando la respuesta es incorrecta, o solo fallan algunos nombres, rastree todo el camino:

dig +trace nexwall.com.br

El rastreo va desde los servidores raíz hasta los autoritativos. Líneas como UDP setup ... failed: network unreachable para direcciones IPv6 son normales en una red sin IPv6; mire la última línea, que da la respuesta final y de dónde vino.
